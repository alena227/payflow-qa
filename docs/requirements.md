# Требования PayFlow

Версия 1.0 · Статус: утверждено для тестирования · Источник: описание стенда, Swagger (`/docs`), README.

Каждое требование имеет ID, на него ссылаются тест-кейсы (`docs/test-cases.md`) — так строится матрица трассируемости.

## 1. Регистрация и вход (AUTH)

| ID | Требование |
|---|---|
| REQ-AUTH-01 | Регистрация по email и паролю. Email валидный, хранится в нижнем регистре, уникален (повтор → 409). Пароль 8–64 символа. Успех → 201, `{id, email}`. |
| REQ-AUTH-02 | При регистрации автоматически создаются два счета пользователя: RUB и USD с балансом 0.00. |
| REQ-AUTH-03 | Вход по email + пароль возвращает JWT (`access_token`, `token_type=bearer`). Неверный email или пароль → 401 с одинаковым текстом `invalid credentials` (не раскрываем, существует ли email). |
| REQ-AUTH-04 | JWT подписан HS256, содержит `sub` (id пользователя), `iat`, `exp`; срок жизни 30 минут. Токен без подписи, с неверной подписью, с другим алгоритмом или истекший → 401. |
| REQ-AUTH-05 | Все эндпоинты, кроме `/health`, `/auth/register`, `/auth/login`, требуют заголовок `Authorization: Bearer <token>`. Без него → 401. |
| REQ-AUTH-06 | После 5 неудачных попыток входа подряд (неверный пароль или неверный код 2FA) вход блокируется на 5 минут → 429. Успешный вход сбрасывает счетчик. |

## 2. Двухфакторная аутентификация (2FA)

| ID | Требование |
|---|---|
| REQ-2FA-01 | Подключение 2FA в два шага: `POST /auth/2fa/setup` выдает секрет и `otpauth_uri`; `POST /auth/2fa/enable` с верным 6-значным кодом включает 2FA. Неверный код → 400, 2FA не включается. |
| REQ-2FA-02 | Если 2FA включена, вход без поля `otp` → 401 `otp required`; с неверным или пустым кодом → 401 `invalid otp`; с верным кодом → 200 и токен. |
| REQ-2FA-03 | Принимается код текущего 30-секундного окна и соседних (±1 окно). |
| REQ-2FA-04 | Отключение 2FA (`/auth/2fa/disable`) только с верным кодом. |

## 3. Счета (ACC)

| ID | Требование |
|---|---|
| REQ-ACC-01 | `GET /accounts` возвращает только счета текущего пользователя. |
| REQ-ACC-02 | `GET /accounts/{id}` возвращает счет только его владельцу; чужой или несуществующий счет → 404 (одинаково, чтобы нельзя было перебирать id). |
| REQ-ACC-03 | Демо-пополнение `POST /accounts/{id}/topup` только своего счета, сумма > 0, ≤ 1 000 000, до 2 знаков после запятой. Создает операцию `topup`. |
| REQ-ACC-04 | Деньги во всех ответах API — строки с двумя знаками после запятой (`"100.00"`). |

## 4. Переводы (TRF)

| ID | Требование |
|---|---|
| REQ-TRF-01 | Перевод `POST /transfers {from_account_id, to_account_id, amount}` — только со своего счета на любой существующий счет (в том числе свой другой валюты). Перевод на тот же счет → 422. Несуществующий/чужой источник или несуществующий получатель → 404. |
| REQ-TRF-02 | Сумма: > 0, ≤ 1 000 000, не больше 2 знаков после запятой. Иначе → 422. |
| REQ-TRF-03 | Комиссия = 1% от суммы в рублевом эквиваленте, но не меньше 10 ₽ и не больше 500 ₽. Для USD-счета комиссия пересчитывается в доллары по курсу. Округление до 0.01 по правилу ROUND_HALF_UP. Комиссия списывается сверх суммы перевода. |
| REQ-TRF-04 | Конвертация RUB↔USD по курсу USD/RUB из сервиса курсов: USD→RUB = сумма × курс, RUB→USD = сумма ÷ курс, округление ROUND_HALF_UP до 0.01. В ответе есть `rate` и `amount_to`. |
| REQ-TRF-05 | Суточный лимит исходящих переводов пользователя — 300 000 ₽ в рублевом эквиваленте по всем его счетам, сутки по UTC. Перевод, после которого сумма за сутки станет **больше** лимита → 422 `daily transfer limit exceeded`. Ровно 300 000 — разрешено. |
| REQ-TRF-06 | Если на счете меньше, чем сумма + комиссия → 422 `insufficient funds`, балансы не меняются. |
| REQ-TRF-07 | Перед списанием вызывается антифрод. Отказ → 403, таймаут/ошибка сервиса → 503. Ошибка сервиса курсов → 503. В этих случаях балансы не меняются. |
| REQ-TRF-08 | Списание, зачисление, комиссия и запись операции выполняются атомарно (одна транзакция БД). Параллельные переводы не приводят к отрицательному балансу и не обходят лимит. |
| REQ-TRF-09 | Комиссия зачисляется на системный счет комиссий в валюте счета-источника. |

## 5. История и уведомления (HIST)

| ID | Требование |
|---|---|
| REQ-HIST-01 | `GET /transactions` — операции текущего пользователя (входящие, исходящие, между своими счетами), новые сверху, пагинация `limit` (1–200) и `offset`. Поле `direction`: `in`, `out`, `self`. |
| REQ-HIST-02 | После перевода отправитель и получатель получают по уведомлению (`GET /notifications`) в течение нескольких секунд. |

## 6. События Kafka (EVT)

| ID | Требование |
|---|---|
| REQ-EVT-01 | После каждого успешного перевода в топик `transactions` публикуется **ровно одно** событие `transfer.completed`, ключ — `tx_id`. |
| REQ-EVT-02 | Событие соответствует JSON-схеме `app/notifier/transaction_event.schema.json`; суммы — строки с 2 знаками; данные совпадают с операцией в БД. |
| REQ-EVT-03 | notifier сохраняет уведомления идемпотентно: повтор того же события не создает дублей. |
| REQ-EVT-04 | Сообщение, которое не является валидным JSON или не соответствует схеме, отправляется в `transactions.dlq` с заголовком `error` и не останавливает обработку следующих сообщений. |

## 7. Данные (DATA)

| ID | Требование |
|---|---|
| REQ-DATA-01 | Баланс каждого счета равен сумме всех зачислений минус сумма всех списаний (с комиссиями) по таблице операций. |
| REQ-DATA-02 | Отрицательных балансов не бывает. |
| REQ-DATA-03 | Деньги хранятся в `NUMERIC(18,2)`, не в float. |

## 8. Безопасность (SEC)

| ID | Требование |
|---|---|
| REQ-SEC-01 | Пользователь не может прочитать или изменить чужие данные (счета, операции, уведомления) — защита от IDOR. |
| REQ-SEC-02 | CORS: API разрешает кросс-доменные запросы только с `http://localhost:8090`; для других Origin заголовок `Access-Control-Allow-Origin` не возвращается. |
| REQ-SEC-03 | Пароли хранятся только в виде bcrypt-хэша. |
| REQ-SEC-04 | Ошибки не раскрывают внутренние детали (стектрейсы, SQL). 500 → `{"detail": "internal error", "request_id": ...}`. |

## 9. Веб-интерфейс (UI)

| ID | Требование |
|---|---|
| REQ-UI-01 | Вход, при включенной 2FA появляется поле кода; понятные сообщения об ошибках. |
| REQ-UI-02 | Отображаются счета с балансами, форма перевода, история, уведомления; после перевода балансы и история обновляются. |
| REQ-UI-03 | Мобильная верстка (ширина от 360 px): нет горизонтальной прокрутки страницы, все элементы формы перевода и суммы в истории видны полностью. |

## 10. Нефункциональные (NFR)

| ID | Требование |
|---|---|
| REQ-NFR-01 | Логи всех сервисов в JSON; у каждого запроса `request_id` (заголовок `X-Request-ID` в ответе), он же передается во внешние сервисы и в заголовки событий Kafka. |
| REQ-NFR-02 | Стенд поднимается одной командой `docker compose up`, сбрасывается к тестовым данным одной командой; потребляет не больше 2–3 ГБ памяти. |
| REQ-NFR-03 | p95 времени ответа `POST /transfers` ≤ 500 мс при 50 одновременных пользователях, доля ошибок < 1% (проверяется в день 11). |
