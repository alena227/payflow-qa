# Отчёт о нагрузочном тестировании PayFlow

**Дата:** 26.11.2026 · **Инструмент:** k6 (Docker-образ grafana/k6) · **Объект:** `POST /transfers`
**Сценарий:** [load/transfer_load.js](../load/transfer_load.js) · **Сборка:** `BUGS=0`, commit `291fe91`+
**Критерии (REQ-NFR-03):** p95 времени ответа < 500 мс, доля ошибок < 1%.

## Профиль нагрузки
Для каждого уровня: разгон 10 c → удержание 40 c → спад 10 c (`ramping-vus`). Создание пользователей и пополнение счетов вынесены в `setup()`, под нагрузкой измеряется только перевод (чтобы дорогая регистрация, bcrypt, не искажала замер). Между итерациями пауза 1 c.

## Результаты

| Виртуальных пользователей | Итераций | p95 перевода | p95 всех запросов | Ошибки | Критерий p95 < 500 мс |
|---|---|---|---|---|---|
| 10  | 483  | 79.8 мс  | 92.8 мс  | 0% | ✅ прошёл |
| 50  | 2270 | 290.7 мс | 308.6 мс | 0% | ✅ прошёл |
| 100 | 3929 | 563.1 мс | 556.6 мс | 0% | ❌ не прошёл |

Пропускная способность: 7.2 → 24.9 → 36.3 переводов/с. Доля ошибок на всех уровнях — **0%**.

## Выводы
- До **50 одновременных пользователей** сервис уверенно укладывается в норматив (p95 ≈ 309 мс).
- При **100 пользователях** время ответа деградирует: p95 = 563 мс, порог 500 мс превышен. При этом **ошибок нет** — система не отказывает, а замедляется. Это точка, после которой нужна оптимизация или масштабирование.
- Переводы атомарны и под нагрузкой не теряются и не дублируются (0% ошибок, все проверки `transfer 201` успешны).

## Ограничения теста
- Прогон выполнен **на ноутбуке**: api и PostgreSQL ограничены 256 МБ памяти каждый, k6 потребляет ресурсы той же машины. Цифры отражают относительную деградацию под ростом нагрузки, а не абсолютную ёмкость прод-сервера.
- Узкое место при росте VU — вероятно, пул соединений с БД (10) и CPU ноутбука. На отдельном сервере с большим пулом порог 500 мс держался бы при большей нагрузке.
- Тяжёлые прогоны (100+ VU, длительные) рекомендуется выполнять в CI (GitHub Actions), а не локально.

## Рекомендации
1. Повторить тест на инфраструктуре, близкой к прод (отдельные хосты для api и БД).
2. Проверить размер пула соединений PostgreSQL и число воркеров uvicorn как первых кандидатов на оптимизацию.
3. Добавить нагрузочный прогон (10 VU, короткий) в CI как smoke-проверку производительности.
